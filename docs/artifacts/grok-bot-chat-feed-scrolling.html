How the Chat Feed Scrolls

Your conversation is a very long book. The app never holds the whole book — it holds the last chapter, and of that chapter, it only builds the two pages you’re looking at.

Two layers, two tricks

Layer 1 · the loaded window

Only the newest slice of messages is in memory. Scroll up and the app quietly asks the server for the previous page, and the one before that. A 10,000-message chat never sits in RAM.

Layer 2 · the virtual shelf

Of the loaded slice, only rows near your viewport are real. Everything else is a paper strip with a height written on it (the zero-jump work made those heights exact for cached media).

Why “Open original” started at the top

The old link-opener lived outside the engine. It could only find a message by looking at real DOM rows — and a far-away message has no DOM at all. So its only move was:

Not a data-structure problem — the engine always knew every loaded row’s exact position. The outsider just never asked it.

The fix: ask the engine (it was there all along)

Now

The app’s own find-in-chat has a teleport: “navigate to this row, centered, smooth.” We exposed it and the link-opener now uses it — plus a blue focus glow on arrival so your eye lands with it.

try teleport → target older than the window? fast-rewind (loads older pages) → retry → snap the moment it loads

For a message older than the loaded window, the engine literally cannot jump to a row it doesn’t have yet — so we rewind a few screens per beat, which is exactly what makes the app pull older pages, and re-try the teleport each beat. It snaps mid-flight the instant the message enters the window, instead of walking every page to the end.

Jump-loading: shipped

Now live

We went the rest of the way — but through a door that was already there. The feed’s own store has a “pull one older page, no scrolling” function (the app’s search-reveal uses it). Deep links now call it directly: the viewport stays put while history streams in behind the scenes, the teleport re-tries each beat, and the jump snaps the instant the target loads. Pages also got wider (100 → 400 messages per fetch).

try teleport → not loaded? pull an older page in place → retry → snap · viewport never moves until the jump

One route was investigated and rejected: faking a “here’s a middle-of-history snapshot” event. The live feed keeps a strict sequence counter — hand it a mid-history window and the next real message trips a full resync that throws the window away, and the fake state leaks into saved-transcript restore, unread markers and bottom-pinning. Streaming pages through the store’s own front door keeps every one of those systems honest.
