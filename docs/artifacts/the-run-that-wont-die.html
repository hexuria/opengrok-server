The Run That Won't Die

Close the app. Kill the process. Reboot the machine the building runs on. The coworker picks up exactly where it was. This is the machinery that makes that true — and the one ordering rule everything else hangs off.

The word

“Harness” means two things. Say which.

Almost every confusing conversation about this subject is two people using the same word for different things.

The shape

A run is a graph, not a function call

If the loop were an ordinary function, its state would live in memory and die with the process. Instead each step is a node that gets written down before it is attempted, so the run’s position is a fact in a database rather than a place in a stack.

The one rule

Write down that you are about to call, before you call

The tempting order is: do the work, then record it. It is wrong, and the reason is a window of time about as wide as a network request.

Pausing

Three reasons a run stops, and only one is interesting

Two of these are ordinary waiting, measured in seconds, and the loop just holds. The third can last a week, so it is a saved state rather than a held breath.

Recovery

Nobody notices a crash. A sweep notices a run nobody is driving.

There is no crash handler, because a process that has died cannot handle anything. Instead the building periodically looks for runs that claim to be in progress and have not moved.

Exactly once

The same answer, sent twice, must land once

People double-tap buttons. Networks retry. A phone and a laptop can both have the same consent card open. So every answer carries the identity of the thing it answers, and the second arrival is recognised rather than applied.

The states

Notice what is not in the list. There is no “cancelled by disconnect”. A window closing is not a state change, because the window was never driving the run — it was watching it.

The invariants

What a run never does

  • Keep its position in memory. The position is a row or it does not exist.
  • Call before it journals. Not once, not for a “cheap” call.
  • Fail because a person walked away. Waiting is a state, not an error.
  • End because a window closed, a process restarted, or a replica died.
  • Get driven by two workers at once. The claim is atomic or it is broken.
  • Apply the same answer twice.
  • Turn a refusal into a crash. Refusals are results.
  • Hold a connection open while a human thinks.

One sentence

Write down what you are about to do before you do it, and a crash stops being an emergency — it becomes a row somebody picks up later.
