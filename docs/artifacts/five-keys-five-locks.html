Five Keys, Five Locks

Every secret in the system is one of five kinds. Each kind has exactly one place it is allowed to rest, one path it may travel, and one blast radius if it leaks. Mixing two of them up is how a password ends up in a transcript.

The map

Five kinds, five homes, and the lines they may not cross

The best trick in the system

Handoff: how a coworker gets logged in without anyone learning the password

A site with no API. The coworker needs to be signed in. The naive answers are all bad: store the password in the vault, or put it in the model’s context, or ask the model to type it. The actual answer is to move the human, not the secret.

The other path

A one-off secret: masked in, used once, gone

Sometimes a tool needs an API key that is not worth an OAuth connection. It travels, it is used, and it is not kept — which means the interesting design work is all about what does not happen at each step.

  1. The coworker says it needs one, and names it“I need SOME_API_KEY to call this.” The run suspends — the same suspension as a consent card, because it is the same kind of wait.
  2. You type it into a masked fieldIn the window. Not echoed, not autofilled into a normal text box, not written into the window’s own storage.
  3. The building relays it without keeping itIt goes to the run that asked. It is not written to the vault, not written to the transcript, and not written to a log line.
  4. It lands in one run’s environment on the deskThe tool that asked can read it. The next run cannot.
  5. The transcript records that a secret was suppliedNot its value. The record says a key named SOME_API_KEY was provided at this step — which is the auditable fact.

When to use a connector instead. If the service has OAuth, use it: a connector token can be revoked centrally, is scoped, and does not need a person present. A one-off secret is for the long tail — the internal service with a static key, the thing nobody has built a connector for yet.

Connectors

The vault, and why tokens are lent rather than copied

A connection belongs to a person or an organisation, not to a coworker. Coworkers are lent the use of it, under a rule, and the lending is what gets revoked — not the token.

The boundaries

The five lines nothing crosses

  • Window → building. A window never holds a desk token, a connector token, or a provider credential. It holds one session: its own.
  • Building → desk. A desk receives its own token and one run’s environment. It never receives the vault, and never a model key.
  • Desk → building. Cookies stay on the desk. The building has no copy and wants none.
  • Anything → the model. The model’s context never contains a credential. Arguments are redacted before the judge sees them, too.
  • Anything → the record. The transcript says that a secret was used, never what it was. Same for logs.

The one to guard hardest. Provider credentials — kind ③ — have the widest blast radius of anything in the system, because they are the only secret that costs money per use and is not scoped to one person or one service. They live on exactly one floor, they never appear on a coworker’s record, and a model pin is a route name rather than a key precisely so that nothing else ever needs to hold one.

One sentence

Name the kind and you know the home; know the home and you know exactly how bad it would be to lose it.
